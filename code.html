Code

A driving robot in a week, a reliable auto by the first event.

FTC code is Java running on the Control Hub inside a project FIRST gives you.

  • This page gets you from a blank laptop to a robot that drives, then through the control theory, localization, and path following that separate a robot that moves from one that scores in autonomous.
  • Library versions checked September 2026.
SDK 12.0Android Studio Narwhal 3+Java 8 syntax

Setup

  1. Install Android Studio (Narwhal 3 Feature Drop or newer for SDK 12). Download from developer.android.com. Accept the SDK components it asks for.
  2. Get the FTC project. In Android Studio: Get from VCS, paste https://github.com/FIRST-Tech-Challenge/FtcRobotController.git, clone. The first Gradle sync takes a while. Your code goes in TeamCode/src/main/java/org/firstinspires/ftc/teamcode/.
  3. Put it in your own Git repo. Fork or push to a team GitHub. Commit after every working change. This is the fix for the "Control Hub got wiped two days before the qualifier" story.
  4. Update the hub. Use the REV Hardware Client to bring the Control Hub OS (1.1.6 or newer) and the Robot Controller app to the season's version. The Driver Station app must match major.minor.
  5. Connect and deploy. USB-C to the hub the first time, then set up wireless ADB so nobody has to crawl under the robot. adb connect 192.168.43.1:5555 while on the robot's Wi-Fi.
  6. Configure the robot on the Driver Hub: name every motor, servo, and sensor by port. Those names are what hardwareMap.get() looks up.

Blocks

  • Drag-and-drop in the browser at 192.168.43.1:8080.
  • Fine for a first week and for a rookie who has never coded.
  • You will outgrow it by the first event.

OnBot Java

  • A Java editor served by the Control Hub itself, same address.
  • No Android Studio, no Gradle.
  • Great for emergency fixes at competition.
  • No libraries, no Git.

Android Studio (Java or Kotlin)

The real path. Libraries, Git, refactoring, autocomplete. Everything on this page assumes it.

Things that break setup, and the fixes detail
  • Gradle sync fails: wrong Android Studio version, or no internet the first time. Match the version in the SDK's README.
  • "App version mismatch" on the Driver Station: RC and DS apps must be the same major.minor. Update both.
  • Deploy takes 40 seconds: normal for a full build. Sloth Load (Dairy Foundation) hot-reloads only TeamCode in about a second; worth setting up once the team is past week two.
  • Hub not found over ADB: you are not on the robot's Wi-Fi, or the hub's Wi-Fi is on a band your laptop cannot see.
  • Library dependency vanished: pin versions in build.gradle and keep the Gradle cache. Prefer libraries on Maven Central or a stable repo.

OpModes and the hardware map

  • Every program is an OpMode: a class the Driver Station lists and runs.
  • LinearOpMode runs top to bottom; TeleOp is a while (opModeIsActive()) loop.
  • Unlike Blocks or VEX, you declare every device in code, by the name from the robot configuration.
  • @TeleOp(name="Drive") or @Autonomous(name="Left Auto") puts it on the Driver Station menu. @Disabled hides it.
  • waitForStart() blocks until the driver presses Play. Everything before it runs on Init.
  • telemetry.addData(...) then telemetry.update() shows values on the Driver Hub. Your first debugger.
  • Never sleep() in a TeleOp loop. It freezes the drivers.
package org.firstinspires.ftc.teamcode;

import com.qualcomm.robotcore.eventloop.opmode.LinearOpMode;
import com.qualcomm.robotcore.eventloop.opmode.TeleOp;
import com.qualcomm.robotcore.hardware.DcMotorEx;
import com.qualcomm.robotcore.hardware.Servo;

@TeleOp(name = "Basic TeleOp")
public class BasicTeleOp extends LinearOpMode {
    @Override
    public void runOpMode() {
        DcMotorEx arm = hardwareMap.get(DcMotorEx.class, "arm");
        Servo pinch = hardwareMap.get(Servo.class, "pinch");

        waitForStart();
        while (opModeIsActive()) {
            arm.setPower(-gamepad1.left_stick_y);
            if (gamepad1.a) pinch.setPosition(0.2);
            if (gamepad1.b) pinch.setPosition(0.7);

            telemetry.addData("arm ticks", arm.getCurrentPosition());
            telemetry.update();
        }
    }
}

Motor setup that saves you later

arm.setDirection(DcMotorSimple.Direction.REVERSE);
arm.setZeroPowerBehavior(DcMotor.ZeroPowerBehavior.BRAKE);
arm.setMode(DcMotor.RunMode.STOP_AND_RESET_ENCODER);
arm.setMode(DcMotor.RunMode.RUN_WITHOUT_ENCODER);

// bulk reads: one transaction per hub per loop
for (LynxModule hub : hardwareMap.getAll(LynxModule.class))
    hub.setBulkCachingMode(LynxModule.BulkCachingMode.AUTO);
  • BRAKE holds a lift when power is zero (electrically, not against gravity).
  • RUN_WITHOUT_ENCODER plus your own PID beats the hub's RUN_TO_POSITION once you know what you are doing. Start with RUN_TO_POSITION if you do not.
  • Bulk caching cuts loop time from tens of milliseconds to a few. Set it once at init.

TeleOp that drivers like

Mecanum drive, robot-centric

double y  = -gamepad1.left_stick_y;   // forward
double x  =  gamepad1.left_stick_x * 1.1; // strafe (counteract imperfect strafing)
double rx =  gamepad1.right_stick_x;  // rotate

double d = Math.max(Math.abs(y) + Math.abs(x) + Math.abs(rx), 1);
fl.setPower((y + x + rx) / d);
bl.setPower((y - x + rx) / d);
fr.setPower((y - x - rx) / d);
br.setPower((y + x - rx) / d);

Field-centric: rotate the stick by the heading first

double h = imu.getRobotYawPitchRollAngles()
              .getYaw(AngleUnit.RADIANS);
double rotX = x * Math.cos(-h) - y * Math.sin(-h);
double rotY = x * Math.sin(-h) + y * Math.cos(-h);
// then use rotX, rotY in place of x, y above
if (gamepad1.options) imu.resetYaw(); // re-zero facing away from driver

Presets, not sticks

  • One button sends the lift to scoring height and another brings it home.
  • The operator should never watch a mechanism and hold a stick.
  • Use a PID or RUN_TO_POSITION toward a saved target.

Do two things at once

  • Raise while driving, retract while returning.
  • In a plain loop this means every mechanism updates every iteration with no blocking calls.
  • Command-based libraries make this natural.

Rising-edge buttons

  • Toggle the claw on the press, not while held.
  • SDK 11.1+ gamepads have edge detection (gamepad1.aWasPressed()); otherwise track the previous state yourself.

Deadband and curves

  • Ignore stick values under about 0.05.
  • Cube the stick (x*x*x) for fine control at low speed and full power at the ends.

Slow mode

Hold a bumper to scale drive power to 0.3 for lining up. Drivers use it more than you would expect.

Telemetry that helps

  • Loop time in ms, battery voltage, lift position and target, "has element" from the intake sensor.
  • If the driver cannot see it they cannot use it.

Control: getting a mechanism to a target

The Control Award is mostly this section done well and written down.

PID in ten lines

double kP = 0.01, kI = 0, kD = 0.0005, kG = 0.08; // tune these
double integral = 0, lastError = 0;
ElapsedTime timer = new ElapsedTime();

double error = target - arm.getCurrentPosition();
double dt = timer.seconds(); timer.reset();
integral += error * dt;
double derivative = (error - lastError) / dt;
lastError = error;
double power = kP * error + kI * integral + kD * derivative + kG;
arm.setPower(Range.clip(power, -1, 1));
  • P does most of the work: power proportional to how far away you are.
  • D damps the overshoot: brakes when the error is shrinking fast.
  • I removes steady-state error, and causes windup if you let it grow. Most FTC mechanisms do not need it.
  • kG (feedforward) is the constant power to hold against gravity. Add it and you can drop I entirely.

How to tune, in order

  1. Find kG. With P at zero, what power just holds the arm level? That is kG (for an arm it scales with cos of the angle).
  2. Raise kP until it reaches the target fast and overshoots a little.
  3. Add kD until the overshoot is gone. Too much and it gets jittery.
  4. Only then consider kI, small, with a clamp on the integral.
  5. Graph it in FTC Dashboard or Panels. Tuning by eye takes ten times longer.

The SDK's built-in RUN_TO_POSITION and setVelocity() are PID loops running on the hub with fixed defaults. They are fine for a first version and for velocity control of flywheels. Your own loop wins once you need feedforward or motion profiling.

Beyond PID: profiles, velocity control, and state machines detail

Motion profiling

  • Instead of asking a PID to jump to the target, feed it a target that moves along a trapezoid (accelerate, cruise, decelerate).
  • Smoother, repeatable, and slides stop slamming.
  • Road Runner and Pedro do this for the drivetrain; a 30-line class does it for a lift.

Velocity control

  • Flywheels and intakes want a speed, not a position.
  • setVelocity(ticksPerSecond) with the hub PIDF, or your own kV × target + PID on the error.
  • Read the current draw to detect a jam.

State machines

  • A scoring sequence (close claw, raise, extend, open, retract) is a set of named states with a transition condition each.
  • Update it every loop.
  • This is how you write a non-blocking auto or a one-button TeleOp macro without sleep().

Loop time

  • Aim under 20 ms.
  • Bulk reads, no unneeded I²C reads, no telemetry.update() more than once per loop, and vision on a coprocessor or in its own thread.

Deep dive: CTRL ALT FTC is the standard control-theory guide written for this level.

Localization: knowing where the robot is

A good autonomous is a localization problem first and a path problem second.

Level 0

Time

  • Drive at power for milliseconds.
  • Different every time the battery changes.
  • Only for a robot that has to move tomorrow.
Level 1

Drive encoders + IMU

  • Distance from the wheels, heading from the gyro.
  • Free, and wrong whenever a wheel slips (mecanum wheels slip a lot).
Level 2

Dead wheels or optical

  • Two or three unpowered odometry pods, fused by a Pinpoint, or an OTOS reading the floor.
  • Accurate to a fraction of an inch over an auto.
  • This is the standard.
Level 3

+ AprilTags

  • Odometry drifts; the tags on the field walls do not.
  • A camera or Limelight corrects the estimate whenever it sees one.

Both Road Runner and Pedro Pathing have Pinpoint localizers built in, so usually you configure it there instead of calling it yourself.

Path following

Pedro Pathing v3, Sept 2026

  • Bezier-curve paths with a reactive follower built for speed.
  • Version 3 added the Foresight follower, a pose factory, a web-based AutoTune, and logging.
  • The library most top teams moved to.
  • Docs and quickstart: pedropathing.com. Visualizer: path generator.
  • Pairs with NextFTC for command-based structure.
  • Tuning is a checklist of OpModes; do them in order and write the constants down.

Road Runner 1.0

  • Trajectory planning with spline paths and motion profiles, plus an "Actions" system for sequencing mechanisms with movement.
  • Stable and well documented; less active development than Pedro.
  • Docs: rr.brott.dev. Not compatible with the old 0.5.x tutorials at learnroadrunner.com.
  • MeepMeep previews trajectories on a field image before you run them.
  • Tuning: the built-in tuning OpModes and FTC Dashboard.
Writing an auto that survives an event detail
  • Start position is everything. Mark it on the tile with tape and a printed jig. Half of "the auto broke" is the robot starting an inch off.
  • Use the wall. Drive into a wall or field element to reset a coordinate when you can. Free localization.
  • Timeouts on everything. Every wait-for-position has a time limit so one stuck mechanism does not freeze the whole 30 seconds.
  • Park. Whatever else fails, end the auto in the parking zone if the game pays for it.
  • Two versions. A safe auto that scores less and a full auto. Choose on the Driver Station based on your partner.
  • Practice with a partner robot on the field. Autos that work alone collide at events.
  • Log it. Write pose, targets, and timestamps to a file or the dashboard so you can see what happened after a bad run.

Vision

AprilTags on the SDK

  • VisionPortal + AprilTagProcessor with a webcam.
  • SDK 12 adds tag clusters and the BIOBUZZ tag library via getCurrentGameTagLibrary().
  • Gives you range, bearing, and a field pose for each tag.
  • Calibrated webcams: Logitech C270, C310, C920.
  • Costs loop time on the hub; stop streaming when you do not need it.

Limelight 3A

  • Runs AprilTag, color, and neural pipelines on its own processor, and hands results to the hub over USB.
  • Limelight3A class in the SDK.
  • Tune pipelines in its web UI.
  • The only programmable vision coprocessor allowed (R702). One per Control Hub.
  • MegaTag2 gives a fused field pose from multiple tags.

Custom OpenCV

  • A VisionProcessor with OpenCV for color blobs, contours, and game-specific detection.
  • The SDK includes color-locator processors for the common cases.
  • Test under venue lighting; every gym is different.

Structuring a codebase

Subsystems

  • One class per mechanism: Drivetrain, Lift, Intake, Claw.
  • Each owns its hardware, exposes intent (lift.goTo(HIGH)), and updates its own control loop.
  • OpModes become short.
public class Lift {
    private final DcMotorEx motor;
    private int target = 0;
    public Lift(HardwareMap hw) {
        motor = hw.get(DcMotorEx.class, "lift");
        motor.setMode(DcMotor.RunMode.STOP_AND_RESET_ENCODER);
        motor.setMode(DcMotor.RunMode.RUN_WITHOUT_ENCODER);
    }
    public void goTo(int ticks) { target = ticks; }
    public void update() { /* PID toward target */ }
    public boolean atTarget() { return Math.abs(target - motor.getCurrentPosition()) < 20; }
}

Command-based libraries

  • Commands are small actions (RaiseLift, OpenClaw) you sequence, run in parallel, and bind to buttons.
  • A scheduler runs them each loop.
  • Same idea as FRC's WPILib, so it transfers.

Constants in one place

  • A Constants class or @Config class for every tuned number: PID gains, servo positions, encoder targets.
  • Dashboard can edit @Config fields live.

Git discipline

  • Commit after every working change with a message a teammate understands.
  • Tag the commit you ran at each event.
  • Never edit on the hub without pushing the change back.

Learning path

  1. Java basics. Variables, methods, classes, loops, if. Codecademy's free Learn Java course covers everything FTC needs.
  2. Drive the robot. The Basic TeleOp above with a mecanum drive. One evening once the hardware works.
  3. Read a sensor, move a servo, control a motor to a position. One mechanism at a time, with telemetry.
  4. PID on the lift, with feedforward. Graph it. This is where you start understanding instead of copying.
  5. Localization plus a path library. Tune it fully before writing the auto.
  6. Refactor into subsystems and commands. Now the TeleOp macros and the auto share code.
  7. AprilTags. Correct odometry from a tag, then use it in auto.

Missions

Mission C1

Drive in a week

  • Clone the SDK, push it to a team repo, deploy a mecanum TeleOp with field-centric drive and slow mode.
  • Telemetry shows loop time and battery voltage.
Done when a non-coder drives it around the room and the loop time is under 20 ms.
Mission C2

Tune a lift

  • Your own PID plus kG on a slide or arm, three preset heights on buttons.
  • Graph position vs target in Dashboard or Panels during tuning.
Done when it settles within 20 ticks in under a second with no visible overshoot, and the gains are in a Constants class.
Mission C3

Localize

  • Pinpoint or OTOS reporting pose on telemetry.
  • Drive a 1.2 m (4 ft) square by hand and return to the start. Record the error.
Done when the reported pose is within 25 mm (1 in) and two degrees after the square.
Mission C4

Score in auto

  • Pedro or Road Runner tuned, one path that scores a game element and parks.
  • Runs 10 times in a row with the same result.
Done when 9 of 10 runs score, and the one that fails still parks.
Mission C5

Tag correction

  • Detect an AprilTag with a webcam or Limelight and print the robot's field pose.
  • Use it to correct odometry once per auto.
Done when a deliberately misplaced start position still ends in the right spot.
